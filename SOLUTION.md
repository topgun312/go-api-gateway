# SOLUTION.md — Логика решения и алгоритм

Документ описывает, как устроен проект **API Gateway с Rate Limiter**: какую задачу
он решает, из каких компонентов состоит и по какому алгоритму обрабатывает каждый
запрос.

## 1. Задача

Нужен защитный прокси-слой перед локальным ИИ-сервисом **Ollama**. Каждый вызов
Ollama — это «дорогая» операция (отвечает ~6 секунд), поэтому прямой доступ к ней
нежелателен. Шлюз должен:

1. **Аутентифицировать** клиента по API-ключу.
2. **Ограничивать частоту** запросов, чтобы защитить апстрим от перегрузки.
3. **Проксировать** валидные запросы в Ollama и возвращать ответ клиенту.

Итог: клиент общается только со шлюзом, а не с Ollama напрямую.

## 2. Архитектура и роли компонентов

```
+--------+  HTTP/1.1 +-----------------------+  HTTP/1.1 +--------+
| Client | ─────────▶ |   API Gateway (Go)   | ─────────▶ | Ollama |
| (curl) |            |  ┌─────────────┐     |            +--------+
|        |            |  │ Rate Limiter │     |
|        |            |  └──────┬──────┘     |
|        |            │         │ Redis      │   ← счётчики лимита
|        |            │   ┌─────▼───────┐    |
|        |            │   │   Redis     │    |
|        |            │   └─────────────┘    |
|        |            │         │ SQL        │
|        |            │   ┌─────▼───────┐    │
|        |            │   │ PostgreSQL  │    │   ← проверка API-ключа
|        |            │   └─────────────┘    │
+--------+            +----------------------+
```

| Компонент | Файл | Роль |
|---|---|---|
| HTTP-сервер | `cmd/gateaway/main.go` | Сборка всех компонентов, запуск сервера |
| Конфиг | `internal/config/config.go` | Настройки из env с дефолтами |
| Модели | `internal/models/models.go` | Структура `User` |
| Storage (Postgres) | `internal/storage/postgres.go` | Проверка ключа в таблице `users` |
| Storage (Redis) | `internal/storage/redis.go` | Клиент Redis для счётчиков |
| Rate limiter | `internal/ratelimit/limiter.go` | Fixed-window лимит через Lua-скрипт |
| Proxy | `internal/proxy/proxy.go` | Пересылка запроса в Ollama |
| Handler | `internal/handlers/gateway.go` | Оркестрация: auth → limit → proxy |

**Ключевая идея:** handler (шлюз) зависит от интерфейсов `UserStore`, `Limiter` и
`RequestProxy`, а не от конкретных реализаций. Это позволяет подменять Redis на
`miniredis`, БД на мок, а апстрим на `httptest` — что и используется в тестах.

## 3. Алгоритм обработки запроса

Каждый входящий HTTP-запрос проходит конвейер из трёх этапов:

```
Запрос клиента
      │
      ▼
 ┌─────────┐  нет ключа ────────▶ 401 "API key required"
 │ 1. AUTH │
 └────┬────┘
      │ есть ключ
      ▼
 ┌─────────┐  ошибка БД ─────────▶ 500 "Internal error"
 │ 2. LOOK-│  ключ не найден ────▶ 401 "Invalid API key"
 │    UP   │
 └────┬────┘
      │ ключ найден
      ▼
 ┌─────────┐  ошибка Redis ──────▶ 500 "Internal error"
 │3. RATE- │  лимит исчерпан ────▶ 429 + Retry-After: 60
 │  LIMIT  │
 └────┬────┘
      │ лимит ок
      ▼
 ┌─────────┐  апстрим недоступен ▶ 502 "upstream unavailable"
 │4. PROXY │
 └────┬────┘
      │
      ▼
 Ответ Ollama пробрасывается клиенту как есть
```

### Этап 1. Извлечение API-ключа — `extractAPIKey`

Ключ берётся из двух источников, по приоритету:

```go
if strings.HasPrefix(auth, "Bearer ") {
    return strings.TrimPrefix(auth, "Bearer ")
}
return r.Header.Get("X-API-Key")
```

1. Заголовок `Authorization: Bearer <key>` (самый приоритетный).
2. Заголовок `X-API-Key: <key>` (фолбэк).

Если ключа нет (`apiKey == ""`) — сразу `401` без обращения к БД.

### Этап 2. Проверка ключа в PostgreSQL — `Store.GetUserByAPIKey`

Параметризованный запрос (защита от SQL-инъекций):

```sql
SELECT id, api_key, name, created_at FROM users WHERE api_key = $1
```

Три исхода:

| Ситуация | Результат | Ответ клиенту |
|---|---|---|
| Строка найдена | `*User` | идём дальше |
| `sql.ErrNoRows` | `nil, nil` | `401 Invalid API key` |
| Другая ошибка (БД упала) | `nil, err` | `500 Internal error` |

Важный нюанс: «ключ не найден» и «ошибка БД» — разные случаи. Пустой результат —
это **не** ошибка, а легитимный ответ «такого пользователя нет» → 401. Сетевая же
проблема — 500, чтобы клиент не путал отсутствие доступа с поломкой сервера.

### Этап 3. Rate limit — `RedisLimiter.Allow`

**Алгоритм: fixed window (фиксированное окно) в 1 минуту.**

1. Ключ счётчика формируется как:
   `ratelimit:<api_key>:<ГГГГ-ММ-ДДTЧЧ:ММ>` (минута в UTC).
2. В Redis атомарно выполняется Lua-скрипт:

```lua
local current = redis.call('INCR', KEYS[1])     -- увеличиваем счётчик
if current == 1 then                            -- это первый запрос в окне
    redis.call('EXPIRE', KEYS[1], ARGV[1])      -- ставим TTL 60 сек
end
return current                                  -- возвращаем новое значение
```

3. Сравниваем `current` с лимитом (по умолчанию 5):
   - `current <= limit` → запрос разрешён, вернуть `(true, current)`.
   - `current > limit` → запрос блокируется, вернуть `(false, limit)`.

**Почему Lua?** `INCR` и `EXPIRE` должны быть атомарными — это исключает гонку,
когда два параллельных запроса одновременно увидели «первый» и не поставили TTL.
Всё выполняется одной командой `EVAL`, без промежуточных round-trip'ов.

**Почему TTL ставится только при `current == 1`?** Окно начинается в момент первого
запроса в минуту и живёт ровно 60 секунд — старый ключ сам удалится, а не будет
перезаписан. Это и есть «фиксированное окно», а не скользящее.

После лимитера шлюз всегда выставляет заголовки (даже при успехе):

```
X-RateLimit-Limit:     5   (общий лимит)
X-RateLimit-Remaining: 3   (limit - текущий счётчик, не ниже 0)
```

При превышении лимита дополнительно:

```
Retry-After: 60
```

и ответ `429 Too Many Requests`.

### Этап 4. Проксирование в Ollama — `OllamaProxy.Proxy`

1. Читается тело входящего запроса (`io.ReadAll`) — иначе его нельзя переслать
   повторно (в Go тело потока можно прочитать один раз).
2. Строится новый `POST`-запрос на `OLLAMA_URL/api/generate` с тем же телом и
   `Content-Type: application/json`. Используется контекст исходного запроса —
   если клиент отменит запрос, апстрим тоже отменится.
3. Запрос уходит через `http.Client` с таймаутом 60 сек.
4. Ошибка сети (Ollama недоступен) → `502 Bad Gateway`.
5. При успехе статус апстрима и тело ответа пробрасываются как есть
   (`io.Copy`). Это корректно работает и для потокового режима `stream: true`.

## 4. Точка входа — `main.go`

Порядок сборки: конфиг → подключение к Postgres (с `Ping`) → клиент Redis
(с `Ping`) → лимитер → прокси → `http.Server` с таймаутами (read 30s,
write 60s) → старт. Любая из недоступных зависимостей — фатальная ошибка,
сервис не стартует.

## 5. Обработка ошибок (сводка кодов ответа)

| Код | Условие | Тело |
|---|---|---|
| `401` | Нет ключа | `{"error":"API key required"}` |
| `401` | Ключ не найден в БД | `{"error":"Invalid API key"}` |
| `500` | Ошибка БД или Redis | `{"error":"Internal error"}` |
| `429` | Лимит превышен | `{"error":"rate limit exceeded"}` |
| `502` | Ollama недоступен | `{"error":"upstream unavailable"}` |
| `400` | Прокси не смог прочитать тело | `{"error":"bad request"}` |

Гарантия: **проксированы могут быть только аутентифицированные и не
превысившие лимит запросы** — недопустимый запрос никогда не дойдёт до Ollama.

## 6. Известные ограничения алгоритма

1. **Рывок на границе окна.** Fixed window сбрасывает счётчик раз в минуту:
   клиент может отправить 5 запросов в 23:59:59 и ещё 5 в 00:00:00 — 10 почти
   подряд. Для строгих лимитов нужен sliding window или token bucket.
2. **Лимит привязан к ключу**, а не к IP: один ключ может использоваться с
   разных адресов, суммарно 5 запросов в минуту.
3. **Ключ в названии Redis-ключа** — сам ключ не хранится в ответах/логах, но
   фигурирует в Redis; при продакшене стоит продумать хеширование.
4. **Без ретраев и балансировки**: апстрим один, политика повторов при `502`
   отсутствует (чтобы не «добивать» и без того недоступный сервис).

## 7. Схема данных

PostgreSQL, таблица `users` (создаётся в `migrations/schema.sql`):

```sql
CREATE TABLE IF NOT EXISTS users (
    id         BIGSERIAL PRIMARY KEY,
    api_key    TEXT        NOT NULL UNIQUE,
    name       TEXT        NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

Счётчики rate limit **не хранятся в БД** — они живут в Redis с TTL 60 секунд и
удаляются сами. Postgres и Redis решают разные задачи: БД — источник истины по
ключам, Redis — эфемерное состояние лимитов.
